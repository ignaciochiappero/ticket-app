**TDD convention**: every `RED→GREEN` task means write the failing test(s) named exactly as quoted, confirm they fail, implement the minimum to pass, then refactor before moving on (`strict_tdd: true`).

**Build order note**: mandatory web views (Phase 5) sit right after the mandatory API (Phases 1-4) and before optional API capabilities (Phases 6-7). A deadline cut after Phase 5 still leaves a fully usable, demoable product - only Comments and the filters are lost.

**Parallel vs sequential**: tasks within a phase are sequential (each e2e file and `TicketDetail.tsx` accumulate scenarios/actions across tasks). Across phases, 1.1 and 1.2 (dependency installs) are independent of each other. Phase 6 (Comments) and Phase 7 (Search and filters) are independent of each other - both only depend on Phase 5 - so a second implementer could take one while the first takes the other. Everything else is strictly sequential.

## Phase 7: Search and Filters (optional)

Slice 7.0 is **not** optional: it is what makes the mandatory board honest.
`GET /tickets` returned every state on one page of 20 while the header printed
the real total, so a board with 37 tickets said "37" and drew 20, with no way
to reach the rest. A single pager cannot fix a board grouped into columns —
page 1 could be twenty `open` tickets and leave "In progress" empty — so the
board asks once per column instead, the way Jira loads a large column.

The earlier plan for 7.2, "the board shows active tickets and hides resolved
ones", was dropped: the board has a Resolved column, and a default that hides
resolved would empty it and make a resolved ticket vanish from the board that
just moved it there. The column shows the last ten completed and grows on
demand.

- [x] 7.0a RED→GREEN `tickets/ticket-query.spec.ts`: with nothing asked, the filter is the caller's scope and nothing else; an asked-for state narrows it; several states combine into one clause; a state filter cannot widen the caller's scope; a resolved-only board is sorted by when the ticket was resolved; any other board is sorted by creation date; every sort carries a tiebreak; an empty state list is treated as no filter at all. Implement `tickets/ticket-query.ts` (pure, no mongoose types) and `tickets/dto/ticket-query.dto.ts`, accepting `?state=` either repeated or comma separated.
- [x] 7.0b Add `resolvedAt` to the ticket, written in the same instant as the `resolved` history event, and index `{ state, resolvedAt }`. "The last ten completed" has to mean the last ten to be completed: sorting them by `createdAt` buries a ticket opened in March and finished today.
- [x] 7.0c RED→GREEN `ticket-board-scope.e2e-spec.ts`: "The board answers only the states it was asked for"; "Resolved tickets are found through the state filter"; "The resolved column is ordered by when each ticket was resolved"; "Each column pages on its own"; "A state filter cannot reach another requester ticket"; "An unknown state is rejected"; "An empty state filter is the same as asking for nothing". All seven pass against MongoDB; the e2e suite is 66 tests over 7 files.
- [x] 7.0d RED→GREEN `TicketsPage.test.tsx`: "asks once per column, so a full column cannot empty another"; "starts the resolved column at ten and says how many there are"; "brings the next ten without touching the other columns"; "stops at the biggest page the API allows"; "drops the button once every resolved ticket is on screen"; "says so when it cannot show every active ticket". The column grows by raising its limit rather than stitching pages together, so one press is one request and the count survives the reload after a drag. The limit is capped at the API maximum: asking past it answers 400 and would blank the board.
